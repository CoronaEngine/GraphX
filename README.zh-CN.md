# Polaris

简体中文 | [English](README.md)

> 当前处于全新架构设计阶段。新的运行时尚未实现，暂不可使用。

Polaris 是一个面向单个长时间软件工程任务的受控 Agent Harness（智能体执行框架）。

它只有一个产品目标：

> **让 Agent 更稳定、正确、可恢复地执行长任务。**

[plan.md](plan.md) 是产品设计与实现的权威依据。

## 为什么需要 Polaris

即使模型能够解决每一个局部问题，长任务仍然经常失败：

- 目标和约束在多轮执行后发生漂移；
- 旧源码、日志和观察结果污染当前上下文；
- 重要事实虽然已经保存，却无法继续影响当前决策；
- 进程中断导致隐式进度全部丢失；
- 已经过期的仓库观察结果在恢复时被当成当前事实；
- 失败动作在前置条件没有变化时不断重试；
- 执行任务的模型在没有独立证据的情况下自行宣布完成。

Polaris 通过运行时机制解决这些问题，而不是要求模型记住更多指令。

## 产品模型

~~~text
用户
  ↓
任务契约（Task Contract）
  ↓
Polaris 控制器（Controller）
  ├── 运行时状态 / 事件存储
  ├── 上下文管理器（Context Manager）
  ├── 模型客户端（Model Client）
  ├── 动作门禁（Action Gate）
  ├── 工具网关（Tool Gateway）
  ├── 检查点 / 恢复机制
  └── 独立验证器（Independent Verifier）
        ↓
本地仓库 + 测试 + Git
~~~

模型负责语义工作：

- 理解需求和代码；
- 建立并修正假设；
- 选择实现策略；
- 编写变更；
- 解释失败；
- 提议下一步动作。

Polaris 负责事实、资源和生命周期：

- 冻结任务契约；
- 构建每一次模型可见的上下文视图（Context View）；
- 校验并执行工具；
- 记录来源信息和工作区影响；
- 建立耐久的动作边界（Action Boundary）；
- 在中断后恢复；
- 独立验证任务是否完成。

## 受控执行循环

每个具有外部可观察结果的动作执行后，控制权都会回到 Polaris：

~~~text
加载权威状态
→ 构建最小上下文视图
→ 调用模型
→ 规范化模型提议的动作
→ 检查动作门禁
→ 执行工具或控制动作
→ 捕获来源信息和工作区影响
→ 追加事件
→ 原子更新状态
→ 继续 / 等待 / 验证
~~~

只读动作可以在边界明确的批次中并行执行。所有变更动作必须串行执行，而且每次变更都必须在下一次模型调用前形成耐久的动作边界。

模型可以申请调用工具、提交语义检查点、请求用户输入或提议完成任务，但不能直接修改机械状态，也不能写入 `DONE`。

## 上下文管理

Polaris 将上下文窗口视为工作集，而不是数据库。

存储策略（Storage Policy）决定：

- 信息是否具有耐久存储；
- 信息能否被精确恢复；
- 恢复信息需要多少成本；
- 信息属于哪个来源和版本。

注意力策略（Attention Policy）决定：

- 当前动作需要看到什么；
- 哪些约束必须处于注意力前景；
- 哪些信息保留在热工作集中；
- 哪些信息转化为紧凑的恢复引用；
- 如何分配注意力预算。

持久化状态与模型可见状态有意保持不同。每次请求模型时，Polaris 都会根据权威状态重新生成上下文投影，而不是沿用不断增长的追加式对话历史。

## 核心不变量

1. **任务契约不能漂移。** 目标、范围、约束和验收标准都来自冻结的任务契约。
2. **状态不能消失。** 每个已完成的外部动作及其下一步动作，都必须在再次调用模型前持久化。
3. **恢复必须感知版本。** 对可变仓库内容的观察必须绑定来源和源版本。
4. **失败必须有界。** 前置条件不变时，同一个失败动作不能无限重复。
5. **变更必须受控。** 只有 Polaris 可以执行工具并修改机械状态。
6. **完成不能由执行者自行认证。** 只有控制器通过独立验证后才能写入 `DONE`。

## 第一版范围

第一版有意只支持：

- macOS；
- 一个可信的本地仓库；
- 一个活动任务；
- OpenAI 这一个模型提供方；
- 一个前台控制器进程；
- 本地文件、搜索、Patch、Shell 和 Git 工具；
- 基于文件的状态、事件、记忆、输出和检查点；
- 一个使用干净上下文的验证器；
- 微基准测试、轨迹重放和端到端长任务评估。

## 明确不做

第一版不会包含：

- 兼容重构前的 Polaris；
- 承载 Codex 或 Claude Code Skill；
- 多模型提供方；
- 多任务或多项目；
- 调度器、队列、守护进程或任务 DAG；
- Dashboard、TUI、IDE 集成或插件系统；
- 数据库、向量存储或知识图谱服务；
- vendoring、安装清单、迁移或跨平台打包；
- 自动合并、推送、发布或远程执行。

只有在 benchmark 提供证据并且 [plan.md](plan.md) 获得相应修改后，才会考虑这些能力。

## 路线图

实现将按照以下顺序推进：

1. 定义失败轨迹、最小数据模型和基线 benchmark；
2. 构建耐久的状态 / 事件内核；
3. 加入受控变更边界；
4. 加入可恢复性感知和注意力感知的上下文管理；
5. 加入独立验证门禁；
6. 执行基线、完整系统和消融长任务评估。

详细架构、指标、里程碑和发布门禁以 [plan.md](plan.md) 为准。
